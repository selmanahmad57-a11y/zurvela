# Bilan e2e — le serveur de scan public, validé en conditions réelles (2026-10-10)

*La dernière épreuve de SÉCURITÉ avant qu'un vrai visiteur puisse scanner. But :
prouver que les gardes du banc (étape 4) tiennent HORS banc, sur un vrai site
public qu'on possède. Cible : `zurvela.com` (à nous, public, derrière
Cloudflare). Dépôt du jeton de vérification à la racine par FTP. UN seul scan.*

## Résultat mesuré

| Garde / étape | Attendu | Mesuré en réel |
|---|---|---|
| `/scanner` sans vérif | refusé | **403** ✓ |
| `/scanner` avant dépôt du fichier (`peutScanner`/vérif bloque) | refusé | **403** ✓ |
| `/scanner` après dépôt (jeton frais) | 202 + scanId | **202**, scanId 43 car. crypto ✓ |
| **Le scan a TRANSITÉ par le proxy** (garde cardinale) | relais = la cible | **`proxy_relais_hotes = ["zurvela.com"]`, refus = []** ✓✓ |
| IDOR : id voisin | 404 | **404** ✓ |
| IDOR : id exact | 200 + rapport | **200**, rapport HTML (1402 o) ✓ |
| État final du scan | terminé | **termine** ✓ |
| Nettoyage du jeton | retiré | **supprimé (404)** ✓ |
| Coût réel | ~0,05 $ acté | **0,001158 $** (site sain, 6 pages, 0 retenue) |

**La garde cardinale est prouvée EFFECTIVE hors banc** : la preuve n'est pas
« le scan a réussi » mais « le proxy a VU et relayé le trafic du scan »
(`relais = zurvela.com`). Un scan qui serait sorti en direct aurait montré
`relais = []` pendant que le scan réussit — ç'aurait été la garde contournée en
silence. Ce n'est pas le cas.

Le rapport rendu (chaîne `/statut` → HTML) dit « Aucune anomalie retenue » —
honnête : `zurvela.com` est propre. La voix sur défauts est déjà prouvée à
l'étape 2 ; ici on testait la SÉCURITÉ, et elle tient.

## Un constat produit (pas une faille) à retenir

Sur un site derrière un CDN (Cloudflare), **un GET sur le chemin du jeton AVANT
que le fichier existe fige un 404** (cache négatif, indépendant d'une query
anti-cache). En flux normal (déposer PUIS scanner), le 1ᵉʳ GET est post-dépôt →
200, aucun souci. Mais un `/scanner` prématuré (visiteur impatient) empoisonne
le chemin de SON jeton : les vérifications suivantes de ce jeton revoient le 404
périmé jusqu'à expiration du cache. **Ce n'est pas un trou de sécurité** : la
vérification échoue FERMÉE (pas de scan sans preuve), ce qui est le bon côté.
C'est un défaut d'UX/robustesse. Mitigation future (étapes publiques) : émettre
un jeton FRAIS à chaque tentative (chemin neuf, jamais empoisonné), ou guider
« déposez le fichier AVANT de lancer ». À traiter quand on câblera l'interface.

## Verdict

Les gardes de sécurité de l'étape 4 tiennent en conditions réelles : rien ne
part sans preuve, tout scan transite par le proxy filtrant, le rapport n'est
accessible que par l'id imprévisible. **Le produit peut techniquement accepter
un vrai visiteur** du point de vue sécurité. Restent les étapes 5-7 (quota dur,
e-mail de livraison, hébergement) et le constat d'UX ci-dessus. Instruments e2e
au scratchpad (non committés : validation ponctuelle, pas construction).
